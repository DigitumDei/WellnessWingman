## Blocking Issues

- Failed or cancelled turns contaminate future history (shared/src/commonMain/kotlin/com/wellnesswingman/healthchat/HealthChatService.kt): The user message is marked COMPLETED before API-key validation or provider execution, so missing-key, provider-failure, and cancellation paths leave it eligible for later requests. Cancellation also leaves a visible PENDING assistant placeholder.
- Missing-key recovery traps the thread (composeApp/src/commonMain/kotlin/com/wellnesswingman/ui/screens/chat/HealthChatThreadScreen.kt): After returning from LLM settings, the thread does not reload configuration or provide a retry path, and the composer remains hidden. The original draft is also cleared before the send outcome is known.
- Persisted tool exchanges cannot be replayed correctly (shared/src/commonMain/kotlin/com/wellnesswingman/healthchat/HealthChatService.kt): Tool calls are flattened into the final assistant row and tool results are appended afterward, losing the required assistant-tool-result-final-assistant sequence and breaking continuation of tool-using conversations.
- Gemini replay fails after primitive tool errors (shared/src/commonMain/kotlin/com/wellnesswingman/llm/GeminiLlmClient.kt): Gemini history reconstruction assumes every tool result is a JSON object, but legitimate tool errors can be JSON primitives. Subsequent sends then fail and mark the assistant message as an error, effectively bricking the thread.

## Non-Blocking Issues

- Conversation previews can select misleading rows (shared/src/commonMain/sqldelight/com/wellnesswingman/db/ChatConversation.sq): Preview selection includes pending, error, and tool rows and lacks a deterministic timestamp tie-breaker, so lists may show blank or stale previews.
- Message ordering is nondeterministic for timestamp ties (shared/src/commonMain/sqldelight/com/wellnesswingman/db/ChatConversation.sq): User and assistant placeholders can share the same createdAt value, while message queries order only by timestamp.
- History truncation can split tool turns (shared/src/commonMain/kotlin/com/wellnesswingman/healthchat/HealthChatService.kt): Limiting raw message rows rather than complete conversational turns can retain tool results without their corresponding tool calls.
- View-model failures can leave stale UI state (composeApp/src/commonMain/kotlin/com/wellnesswingman/ui/screens/chat/HealthChatThreadViewModel.kt): Load and send paths lack complete exception-safe state handling, allowing Loading or isSending to remain active after repository or settings failures.
- Unknown message statuses default unsafely (shared/src/commonMain/kotlin/com/wellnesswingman/db/ChatConversation.kt): Unknown stored status values are mapped to COMPLETED, which can make corrupt or newer records eligible for provider history.

## Missing Tests

- Verify failed and missing-key user turns are excluded from the next provider request.
- Verify cancellation removes or marks both incomplete user and assistant records.
- Verify recovery after returning from API-key settings, including draft retention and retry.
- Verify exact persisted and reconstructed ordering for single and multiple tool rounds.
- Verify Gemini handling of primitive and errored tool-result content.
- Verify history truncation preserves complete conversational turns.
- Verify preview selection ignores pending, error, and tool rows.
- Verify view-model load, settings, send, and reload exception paths reset UI state.

## Disputed Issues

- The severity of orphaned PENDING assistant rows is disputed between blocking and near-blocking; the row is visible and pollutes the thread but is excluded from model history.
- Deletion confirmation, import ordering, last_insert_rowid connection behavior, and transaction scope were raised as concerns but lack sufficient evidence or are not explicit acceptance failures.

## Outstanding Concerns

- Tool-result replay also drops the isError signal, so errored tool executions lose semantic context even after structural replay is corrected.
- The pre-provider persistence sequence is not transactional, so process termination can leave partial conversations or pending rows; any transaction should cover only short database mutations, not the network call.

```text
Blocking Issues

- None that would crash the app or break the build. The defects below are real but either get swallowed by `HealthChatService.sendMessage`'s catch-all (so they surface as `ProviderError`/degraded UX rather than crashes) or are test/UX gaps.

The asymmetry means a single corrupted `role` row throws on load (failing the whole thread/list), while a corrupted `status` is silently normalized. Either both should be defensive or both strict.

- Import ordering in `MainScreen.kt`: `com.wellnesswingman.ui.screens.chat.HealthChatListScreen` is inserted before `com.wellnesswingman.ui.screens.calendar.day.*`, which breaks the alphabetical/package ordering the rest of the file follows. If ktlint/detekt import sorting is enforced in `./gradlew check`, this will fail CI; if not, it's a style nit.

- No unit tests for `HealthChatListViewModel` or `HealthChatThreadViewModel`. State transitions (Loading→Success/Error/ApiKeyMissing, `isSending` guarding double-send, `NotFound`→Empty, refresh-after-delete) are untested. Given the AGENTS.md testing guidance and that these are the screens backing the issue's success criteria, this is a notable gap.

- No test that `sendMessage` propagates `CancellationException` (the catch rethrows it, but there's no coroutine-cancellation test asserting it isn't turned into `ProviderError`).

- No test for `HealthChatService.renameConversation` (the public API) or for `deleteConversation` via the service.

- No test asserting the v9→v10 migration backfills the `status` default on pre-existing rows (the migration test inserts a row without `status` before migrating but never reads it back to confirm `status = 'completed'`).

Strong Concerns

- The `sendMessage` flow is not wrapped in a transaction. Conversation creation, user-message insert, status update, assistant-placeholder insert, LLM call, tool-result inserts, and assistant update are independent statements. A process kill between the user insert and the status flip leaves a PENDING user row. The model loses the signal that the tool failed.

The Gemini non-object tool-result crash and the latest-message tie-break are the items I'd want fixed before merge; the rest are test-coverage and UX gaps consistent with a first cut.
