## Executive Summary

This branch adds OpenRouter as a third LLM provider by implementing OpenRouterLlmClient (a near-verbatim clone of OpenAiLlmClient with host/header/model changes), wiring it through the provider enum, factory, settings persistence, UI, ViewModel, and analysis orchestrator. The structural wiring is internally consistent and CI passes. However, all three reviewers converged on a single blocking defect: OpenRouterLlmClient.transcribeAudio() uses openai-kotlin's TranscriptionRequest(FileSource(...)), which serializes as multipart/form-data, while OpenRouter's STT endpoint requires application/json with a base64 input_audio payload. This broken path is reachable with no guard from all three voice-note call sites (PhotoReviewViewModel, EntryDetailViewModel, UserCommentsManager) via createForCurrentProvider(), and the mock-based test suite cannot detect it. Because the branch explicitly targets end-to-end OpenRouter support as a peer provider implementing the full LlmClient contract, a deterministic failure on the transcription path is a user-visible regression that blocks merging.

## Blocking Issues

- transcribeAudio sends wrong wire format to OpenRouter STT (shared/src/commonMain/kotlin/com/wellnesswingman/domain/llm/OpenRouterLlmClient.kt): OpenRouterLlmClient.kt:101-109 calls openai-kotlin's TranscriptionRequest(FileSource(...)), which serializes as multipart/form-data with a 'file' field. OpenRouter's /api/v1/audio/transcriptions endpoint requires application/json with input_audio.data (base64), input_audio.format, and model. The format mismatch will cause a 4xx rejection at runtime. All three voice-note paths (PhotoReviewViewModel, EntryDetailViewModel, UserCommentsManager) route through createForCurrentProvider() into the OPENROUTER factory branch with no provider-specific guard. Note: openai-kotlin has no code path to emit the required JSON body shape, so the fix requires a custom HTTP call or an explicit unsupported/degraded-gracefully path — not a parameter change.

## Non-Blocking Issues

- providerId inferred by javaClass.simpleName substring matching (shared/src/commonMain/kotlin/com/wellnesswingman/domain/analysis/AnalysisOrchestrator.kt): AnalysisOrchestrator.kt:127-135 uses class-name string matching to determine provider identity. The new OpenRouter branch is correctly ordered and does not collide with the OpenAI check. The else -> 'unknown' fallback is a behavior change from the prior else -> 'gemini' default for unrecognized clients. Pre-existing design debt, but this branch extends reliance on it; a providerId property on LlmClient would be more robust.
- Heavy code duplication between OpenRouterLlmClient and OpenAiLlmClient (shared/src/commonMain/kotlin/com/wellnesswingman/domain/llm/OpenRouterLlmClient.kt): OpenRouterLlmClient duplicates approximately 270 lines of OpenAiLlmClient verbatim, including the same underlying openai-kotlin OpenAI client. A host/header-parameterized base class would have made the transcription divergence structurally visible rather than hidden in copy-pasted code. Acceptable as first-cut debt, but worth tracking.

## Missing Tests

- transcribeAudio test (OpenRouterLlmClientTest.kt:242) mocks api.transcription(any()) and only asserts returned text — it never captures TranscriptionRequest to verify model id, request shape, content type, or host; the test name overpromises and would pass regardless of what format or model is sent
- No test asserts OpenRouter-specific configuration: host (openrouter.ai/api/v1/), HTTP-Referer and X-Title headers, or base-URL wiring — the only genuinely OpenRouter-specific code is entirely untested because every test injects mockk<OpenAI>()
- No analyzeImage test for OpenRouterLlmClient despite image analysis being the core app path
- No test for outgoing model field in generateCompletion/buildRequest — ModelId(this@OpenRouterLlmClient.model) wiring is unverified
- No LlmClientFactory test asserting OPENROUTER -> OpenRouterLlmClient dispatch
- No AnalysisOrchestrator test asserting providerId = 'openrouter' is saved
- No SettingsAppSettingsRepository round-trip test for OpenRouter key/model or DEFAULT_OPENROUTER_MODEL resolution

## Disputed Issues

- Whether openai/whisper-1 is a valid OpenRouter model slug: Claude's round-2 review states current docs show only openai/whisper-large-v3; Codex states docs list openai/whisper-1 as a valid example. Consensus position is that slug validity is unproven either way and is secondary to the wire-format blocker — the transcription path fails on format before model routing matters.
- Whether transcription is in scope for this PR: OpenCode initially framed it as tangential/inherited debt; Claude and Codex argued it is in scope since issue #140 explicitly lists transcribeAudio as part of the LlmClient contract to implement and the branch presents OpenRouter as a peer provider. Critiques and judge consensus sided with the blocking classification.

## Outstanding Concerns

- The fix for the transcription wire-format mismatch is non-trivial: openai-kotlin structurally cannot emit OpenRouter's required JSON base64 body, so the implementation requires either a raw HTTP call bypassing the SDK, a separate HTTP client for STT, or explicitly marking transcribeAudio as unsupported for OpenRouter with a graceful error. The cost of the correct fix should be understood before re-review.
- responseFormat = ChatResponseFormat.JsonObject is sent unconditionally when a jsonSchema is provided, matching the OpenAI client. OpenRouter routes to heterogeneous models, some of which may reject this field. This is speculative and unverified, but more likely to surface on OpenRouter's catalog than on OpenAI's.
